# Failure-injection audit

**Source:** HLD decisions doc, "M5 · wk 8-9 · Hardening for production": "Failure-injection suite:
fabricated success, empty diff, wrong file, budget overrun, step tampering, cache replay. Each must
be caught." Plus issue #28's "multi-worker load test with no lost or double-run tasks."

This is a record of what is already true as of this commit, not a description of new behaviour. It
checks each named scenario against the current test suite and code, with `file:line` citations.
Paths without a `control-plane/` prefix are relative to the repo root (the Rust crates and the
`mergit_receipt` type stub live outside this subtree); all other paths are relative to this
`control-plane/` directory. See `docs/superpowers/plans/2026-11-01-failure-injection-audit.md` in
the main worktree for the plan this audit closes out.

| HLD scenario | Status | Evidence |
|---|---|---|
| Fabricated success (agent claims done, nothing actually passed) | **Already covered, structurally and by test** | The `finish` tool (`mergit_worker/tools.py:72-81`) takes only a `summary` string — there is no field anywhere an agent could set a success flag; only Φ decides. `tests/test_harness.py:175-178` `test_finish_alone_does_not_complete_the_task` drives this through the real pipeline: agent calls `finish`, `outcome.holds is False`. Nothing to add. |
| Wrong file (agent edits outside the task's intended paths but the literal check still exits 0) | **Already covered** | `tests/test_phi.py:27-32` `test_change_outside_allowed_paths_fails_even_when_check_passes` does exactly this: writes the allowed fix plus an out-of-scope file, command exits 0, `holds is False`. Nothing to add. |
| Empty diff passing | **Accepted behaviour by design, not a defect** | `README.md:307-308` and `README.md:315-316` (the pull-request gate, plan task O9): an empty patch — a task that passed without changing any tracked file — is explicitly not treated as a blocker, and is skipped (not failed) when applying a plan's combined diff, because `git apply` itself refuses an empty patch. This is a documented, intentional outcome of the gate design, not a gap: a task can legitimately pass Φ without producing a change (e.g. a check that was already satisfied), and penalizing that would make the gate stricter than the predicate it is supposed to trust. No test needed; a test here would only assert that the system does what it is already documented to do. |
| Budget overrun | **Fully covered; the one real gap found by this audit is now closed** | `tests/test_harness.py:201-213` `test_budget_exhausted_still_seals_with_phi` proves sealing happens and the *partial, already-useful* work still passes Φ (`outcome.holds is True`). `tests/test_harness.py:245-250` `test_budget_too_small_for_one_token_stops_before_calling` stops the loop with zero model calls. Until this plan, nobody had checked that running out of budget with **no completed work** ends in a recorded failure rather than a silent pass or an unresolved state. Task 1 closed this: `tests/test_harness.py:253-262` `test_budget_exhausted_with_no_completed_work_fails` builds a job with `budget_usdc_units=1` (too small for even one output token) against the default unfixed sandbox state, and asserts `llm.calls == 0`, `outcome.notes == ["cost_budget"]`, and `outcome.holds is False`. The test passed against the harness unmodified — the harness already propagated Φ's real result; this is new permanent coverage of a previously-unexercised branch, not a bug fix. |
| Step tampering (a receipt's hash chain or signature is altered after sealing) | **Covered in the Rust crates; now also exercised from Python by this repo's own tests** | `spec/vectors/*.json` (`bad_signature.json`, `chain_mismatch.json`, `root_mismatch.json`, `seq_gap.json`, `seq_order.json`, `commitment_mismatch.json`, `body_hash_mismatch.json`) are consumed by `verifier/tests/vectors.rs` and `spec/tests/attestation.rs` — out of this Python repo's language and ownership (Yash's track); this audit does not re-verify that suite, only confirms it exists and is the origin of the tamper-detection logic. `mergit_receipt.verify()` is exposed to Python at `runtime/py/mergit_receipt.pyi:8`. Task 2 added three tests in `tests/test_harness.py` that drive a real sealed bundle through a **copy**, mutated the way an attacker would after `seal_with_phi()` returns, and confirm the control plane's own `verify()` call — not just the Rust crate's internal tests — flags it: `test_tampered_step_output_is_rejected` (`tests/test_harness.py:71-83`, flips one character of a non-final step's `output_digest`), `test_reordered_steps_are_rejected` (`tests/test_harness.py:86-97`, swaps two non-terminal steps' positions in the `steps` array), and `test_dropped_step_is_rejected` (`tests/test_harness.py:100-110`, removes one non-terminal step entirely — CLAUDE.md invariant 1's "complete trajectory" check, proven from the Python side). Each asserts concretely that `result["status"] != "unattested_valid"` and `result["reasons"]` is non-empty, and the untampered baseline (`test_fake_agent_fixes_repo_and_phi_holds`, `tests/test_harness.py:47-60`) is asserted to round-trip as `"unattested_valid"` first. |
| Cache replay (a stale cached tool/model response reused and presented as fresh) | **Not buildable here — the feature it would guard doesn't exist yet** | The only "cache" fields in this codebase are `cache_read_tokens`/`cache_write_tokens` for *billing* (`mergit_worker/meter.py:104-114`, `mergit_cp/llm.py:35-36`) — they record how many tokens a provider served from its own cache for cost-accounting purposes, with no notion of freshness or replay. There is no cache-provenance field on a receipt step, no cache store, and nothing a step could replay. Writing a test for a replay guard would mean inventing both the feature being guarded and the test for it, which is not what this audit is for. This is recorded as blocked, in the same category as TEE attestation and the Rust-side audit rate mentioned in the reputation plan: it needs a receipt-schema decision first (Yash/mergit-research), not a Python-side task. |
| "No lost or double-run tasks" under concurrent workers (issue #28) | **Already covered** | `tests/test_jobs.py:126-143` `test_concurrent_workers_never_claim_the_same_job` asserts exactly this ("none lost, none twice") against a real Postgres container, running 6 worker threads against `SELECT ... FOR UPDATE SKIP LOCKED` and checking `len(claimed) == len(set(claimed)) == 30` and `set(claimed) == ids`. Nothing to add. |

**Summary:** five of seven named items were already guarded and already tested before this plan; one
(empty diff) is accepted-by-design, not a defect; one (cache replay) cannot be built without a schema
decision that is not this plan's to make. The one real gap (budget overrun with zero completed work)
is now closed by a new test, and step tampering now has Python-side proof in addition to the existing
Rust-side vector suite.
