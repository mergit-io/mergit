# Verifiable Execution Receipt, version 0

**Status:** normative for the v0 build. Schemas: [`schemas/`](schemas/). Test vectors: [`vectors/`](vectors/),
generated by the Rust `mergit-receipt` crate. Where this document and the vectors disagree, the defect is
reported and both are fixed together.

A receipt records one task's complete trajectory, commits to it with a hash chain and a Merkle root, and is
signed by the runtime. Version 0 has no TEE: every receipt says so, and no verifier may call it attested.

## Conventions

- **Hash:** keccak-256. Written as `0x` plus 64 lowercase hex characters.
- **Canonical JSON:** RFC 8785 (JCS). `H(x)` below means `keccak256(JCS(x))`.
- **Address:** `0x` plus 40 hex characters. Inputs may use any case; inside every hashed object addresses are
  written in lowercase, which is how the Rust crates serialise them.
- **Amounts:** USDC base units (6 decimals) as decimal strings.
- **Time:** RFC 3339 in UTC, milliseconds, `Z` suffix.

## Header

| Field | Meaning |
| --- | --- |
| `version` | `"mergit-receipt/0"` |
| `task_id` | `keccak256(abi.encodePacked(plan_id, uint32 index, uint32 attempt))` |
| `plan_id` | `keccak256(utf8(plan_uuid))` |
| `requester` | Requester address |
| `agent_id` | Agent id in the Identity contract, decimal string |
| `category` | Task category, for example `"test-repair"` |
| `phi` | The approved predicate ([predicate-v0.md](predicate-v0.md)) |
| `phi_hash` | `H(phi)`; a builder refuses a header where this does not match |
| `budget_usdc_units` | The task budget |
| `runtime_image` | Identifier of the runtime image |
| `attestation` | `{"kind": "unattested", "dev_key": <address of the signing key>}` in v0 |
| `started_at` | When execution started |

## Steps

| Field | Meaning |
| --- | --- |
| `seq` | 1, 2, 3, … with no gaps |
| `type` | `model_call`, `tool_call`, `command`, `artifact_write`, or `phi_eval` |
| `input_digest`, `output_digest` | keccak-256 of the raw input and output bytes |
| `exit_status` | Integer, or `null` where it does not apply |
| `cost` | `{model, input_tokens, output_tokens, tool_calls, wall_ms, usd_micros}`; `model` may be `null` |
| `at` | When the step finished |

The raw bytes behind every digest travel separately as **blobs**, keyed by digest. Captured output is
capped (1 MiB, 1048576 bytes, by default); when truncated, the stored bytes end with
`\n[mergit: output truncated at <cap> bytes]\n`, where `<cap>` is the cap that was applied, and the digest
covers exactly the stored bytes. At the default cap the marker is `\n[mergit: output truncated at 1048576 bytes]\n`.

**The `phi_eval` step.** Exactly one. It is the last step and it is in the evidence set. Its input bytes
are `JCS(phi)` and its output bytes are `JCS(PhiResult)`. Only sealing creates it, after the agent has
stopped; no other path can append one.

## Commitment

```
leaf_i = H(step_i)
h_0    = H(header)
h_i    = keccak256(h_{i-1} ‖ leaf_i)                 (32 + 32 bytes)
terminal_hash = h_n
root   = Merkle(leaf_1 … leaf_n)
```

**Merkle tree:** build layers upward. Each pair `(a, b)` hashes to `keccak256(min(a, b) ‖ max(a, b))`,
comparing as 32-byte big-endian numbers. When a layer has an odd number of nodes, the last one moves up
unchanged. One leaf: the root is that leaf. Proofs verify with OpenZeppelin `MerkleProof.verify`.

## Sealed receipt

```
SealedReceipt {
  header, steps, evidence: [seq, ...] (sorted, unique),
  meter: {input_tokens, output_tokens, tool_calls, wall_ms, usd_micros}   (sums over all steps),
  ended_at, root, terminal_hash, body_hash, signature
}
body_hash = H(SealedReceipt without the body_hash and signature fields)
```

**Signature:** EIP-712, by the runtime signing key, 65 bytes as `0x` plus 130 hex characters
(`r ‖ s ‖ v`, `v` in {27, 28}).

```
domain  = {name: "Mergit", version: "0", chainId, verifyingContract: <ReceiptRegistry address>}
Receipt(bytes32 taskId, bytes32 root, bytes32 terminalHash, bytes32 bodyHash, uint256 costMicros)
costMicros = meter.usd_micros
```

ReceiptRegistry recovers the signer on chain and requires it to be the agent's registered runtime key.

## Bundle

What the receipt store accepts and serves:

```
Bundle { receipt: SealedReceipt, blobs: {digest: base64(bytes)} }
```

Every digest named by an evidence step must have its blob. Blobs of non-evidence steps may be included; the
store accepts them, and a challenger may request them.

## Verification

A verifier collects every failing reason; it does not stop at the first. Status is `invalid` if any reason
other than `UNATTESTED` is present, otherwise `unattested_valid`. Version 0 has no `valid` (attested)
outcome.

| Code | Meaning |
| --- | --- |
| `SEQ_GAP` | `seq` does not run 1…n without gaps |
| `SEQ_ORDER` | Steps are not in `seq` order |
| `CHAIN_MISMATCH` | Recomputed `terminal_hash` differs |
| `ROOT_MISMATCH` | Recomputed `root` differs |
| `BODY_HASH_MISMATCH` | Recomputed `body_hash` differs |
| `BAD_SIGNATURE` | The signature does not recover, or recovers to a key other than the expected one |
| `PHI_HASH_MISMATCH` | `phi_hash` differs from `H(phi)`, or the `phi_eval` input is not `JCS(phi)` |
| `NO_PHI_EVAL` | No `phi_eval` step |
| `PHI_EVAL_NOT_LAST` | A `phi_eval` step that is not the last step, or more than one |
| `PHI_EVAL_NOT_EVIDENCE` | The `phi_eval` step is not in the evidence set |
| `METER_MISMATCH` | Meter totals differ from the sums over steps |
| `BLOB_MISSING` | An evidence step's input or output blob is absent |
| `BLOB_DIGEST_MISMATCH` | A blob's keccak-256 differs from its key |
| `PHI_RESULT_CONTRADICTED` | Recorded `holds` differs from the recomputation in [predicate-v0.md](predicate-v0.md) |
| `COMMITMENT_MISMATCH` | Root, terminal hash, body hash or cost differs from the on-chain commitment |
| `ATTESTATION_UNSUPPORTED` | The attestation kind is not `unattested`; a v0 verifier cannot check it, so the receipt is invalid |
| `UNATTESTED` | Informational: the receipt carries no hardware attestation. Present on every v0 receipt |

## Verdicts

The validator maps a report to one of three verdicts: `invalid` when the status is `invalid`; otherwise
`pass` when `Φ` holds and `fail` when it does not. `fail` is an honest miss (refund, no slash); `invalid` is a
false receipt (refund and slash).
